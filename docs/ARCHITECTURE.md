# Архитектура

## Избран стек

| Слой | Избор | Защо |
|---|---|---|
| Frontend + Backend | **Next.js 16 (App Router, TypeScript)** | Един проект и един deploy за UI, сървърна логика (Server Actions) и API (Stripe webhook). Статичните страници се пререндерират и се сервират от CDN. |
| База данни + Auth | **Supabase** (PostgreSQL + Supabase Auth) | Безплатен план с Postgres, вградена автентикация (имейл/парола, възстановяване на парола, сигурни сесии) и Row Level Security. Не пишем и не поддържаме собствен auth. |
| Плащания | **Stripe** (Checkout + Customer Portal + webhooks) | Картовите данни никога не минават през нашия сървър. |
| QR генериране | **uqr** (~10 KB, без зависимости) + собствен рендер | Кодът се генерира в браузъра: нулев сървърен разход. Връща матрица и типа на всеки модул → лесно добавяне на стилове, лого, рамки. |
| Стилове | Обикновен CSS с дизайн токени (`globals.css`) | Без Tailwind/UI библиотеки — нула runtime зависимости, светла/тъмна тема. |
| Хостинг | **Vercel** (старт) → Vercel Pro / Netlify / VPS | Виж „Хостинг“ по-долу. |

### Защо не .NET?
ASP.NET Core е отличен избор технически, но за този продукт Next.js печели по три критерия:
1. **Цена на хостинга** — Next.js има щедри безплатни планове (Vercel/Netlify) с CDN; за .NET безплатните опции са с „заспиване“ и бавен старт (Render) или с дневен CPU лимит (Azure F1).
2. **Скорост на разработка** — UI и сървърната логика са в един език и един проект; Supabase и Stripe имат официални JS SDK.
3. **Генерирането в браузъра** изисква JavaScript така или иначе.

### Supabase срещу Neon
| | Supabase Free | Neon Free |
|---|---|---|
| PostgreSQL | ✓ (500 MB) | ✓ (0.5 GB) |
| Вградена автентикация | ✓ имейл, OAuth, magic link, reset | Отделен продукт / трябва собствен auth |
| Row Level Security с JWT на потребителя | ✓ готово | Ръчно |
| Ограничение | Пауза след 7 дни без активност | Cold start след неактивност |

**Избор: Supabase** — спестява цял модул (auth + имейли + сесии), който иначе трябва да се напише, тества и поддържа. Паузата не е проблем за сайт с реален трафик; при растеж Pro планът е $25/месец. Лимитите се променят — проверявайте актуалните цени.

### Хостинг
- **Разработка и бета:** Vercel Hobby (безплатно). ⚠️ Hobby планът е за некомерсиална употреба — при включване на плащания преминете на **Vercel Pro** (~$20/месец) или на **Netlify** (безплатният план позволява комерсиална употреба), или на евтин **VPS** (`next build && next start`, напр. Hetzner ~€4/месец).
- Кодът не използва Vercel-специфични API, затова смяната на хостинг не изисква промени.

### Имейли
Supabase Auth изпраща имейлите за потвърждение и смяна на парола. Вграденият SMTP е само за тестове (много нисък лимит), затова за продукция се настройва собствен SMTP — **Resend** или **Brevo** имат безплатни планове. Настройва се в Supabase → Authentication → SMTP, без промени в кода.

## Модел на данните

```
auth.users (Supabase)
   │ 1:1                 1:1                     1:N
   ├── profiles      ├── subscriptions       └── qr_codes ── 1:N ── qr_scans
   │   email, name   │   plan, status,           name, type, content(jsonb),
   │                 │   stripe_* ids            payload, design(jsonb),
   │                 │                           is_dynamic, short_code, target_url
stripe_events (идемпотентност на webhooks)
```

- `profiles` и `subscriptions` се създават автоматично от тригер при регистрация (план `free`).
- `content` пази стойностите от формата (за редакция), `payload` — кодирания текст, `design` — цветове и бъдещи стилови опции. JSON полетата позволяват нови типове и опции **без миграции**.
- `qr_scans` и динамичните колони са подготвени за статистика и динамични кодове.

## Поток на запис на QR код

1. Браузърът валидира формата и показва кода на живо (`lib/qr/types.ts`, `render.ts`).
2. „Запази“ извиква Server Action (`lib/qr/actions.ts`). Той проверява сесията, оставя само позволените полета (`sanitizeValues`), **генерира payload-а наново на сървъра** и почиства дизайна.
3. Записът минава през Supabase с правата на потребителя: RLS + права по колони + тригер за лимита.
4. `refresh()` обновява таблото без допълнителни заявки от клиента.

Изображенията **не се пазят** — те се генерират в браузъра от `payload` + `design` при показване и изтегляне. Така няма разходи за файлово хранилище.

## Модел на сигурност

1. **RLS навсякъде.** Потребителят вижда и променя само своите редове. Проверено с автоматичен тест (виж README).
2. **Права по колони.** Клиентът може да пише само `name, type, content, payload, design` в `qr_codes`; броячът на сканирания и динамичните полета са само за сървъра. `subscriptions` е само за четене.
3. **Лимитите на плана се проверяват и в базата** (тригер `qr_codes_guard`), не само в UI — заобикаляне през API е невъзможно.
4. **Тайните ключове** (`SUPABASE_SERVICE_ROLE_KEY`, `STRIPE_*`) се ползват само в сървърен код (`import "server-only"`).
5. **Двойна валидация:** `lib/qr/types.ts` се изпълнява и в браузъра (мигновена обратна връзка), и на сървъра (преди запис).
6. **HTTP заглавки за сигурност** (`next.config.ts`): HSTS, X-Frame-Options, nosniff, Referrer-Policy.
7. Не се пазят платежни данни и IP адреси.

## Как се разширява

| Задача | Къде |
|---|---|
| Нов тип QR (напр. „Събитие“) | Нов запис в `QR_TYPES` (`lib/qr/types.ts`) — формата, валидацията и кодирането се появяват автоматично. |
| Нова дизайн опция (форма на точките, лого) | Ново поле в `QrDesign` + `sanitizeDesign` + рендерът в `render.ts`. `uqr` дава типа на всеки модул (finder, timing…). |
| Нов план или лимит | `lib/plans.ts` + функциите `plan_*` в нова миграция. |
| Динамични кодове | Маршрут `app/r/[code]/route.ts` → търси `short_code`, записва `qr_scans`, пренасочва към `target_url`. |
